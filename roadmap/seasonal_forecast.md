# Seasonal forecast scenario: roadmap

Status: local experimental BFA pilot wired into Step 2 (2026-10-30). Two draft runs (May and October 2026) are discovered under the configured local data root. Catalogue/manifests, adjusted monthly weather construction, full-population target-month prediction and member integration are implemented. The October run for November-January completed with 51 members, both directly and through the running app with its default t-only binned model. Forecast-off BFA parity is exact for original and resample residuals. Draft runs remain hidden on Posit Connect; forecast skill and scientific usefulness are not established. Step 3 policy runs with forecast windows are explicitly blocked until its annual exposure contract is extended. The data pipeline lives in `wise-app-data` (`dev/forecast_handover.md`, `dev/forecast_pipeline_plan.md`); this file covers the app side and the hand-off between the two. Review findings of 2026-11-02 (comparator, performance, chart coverage, upstream schema) are in `roadmap/seasonal_forecast_review.md`.

## Design decisions made

- A forecast is one more weather state next to Historical and the SSPs: one dated target window by ensemble member (51 for SEAS5), not a historical year plus a delta. Everything after the weather step (predictors, model, residuals, metrics, Step 3 levers) is reused.
- Forecast can run in the same simulation as SSPs.
- The forecast is unavailable, with a stated reason, when the country has no forecast data or the fitted model uses a weather variable the forecast does not provide (currently anything other than `t`).
- Forecast has its own flyout. Simulation settings holds what applies to every scenario (survey, historical period, residuals, coefficient uncertainty). The historical period does not affect the forecast: the pipeline anchors it to fixed reference years.
- The "Include seasonal forecast" checkbox defaults to off, because a run over 51 members adds run time.
- The forecast scenario is listed before the SSPs in the expected run order, and a run signature carries a `forecast` entry only when the forecast is on, so runs without it keep their existing signature.
- **Adjusted values, no app-side bias correction (confirmed 2026-10-30).** The pipeline publishes `t = era5land_mean + (t_raw - hindcast_mean)`, and the app applies no hindcast arithmetic and never adjusts a forecast value again. The published run manifest declares `adjustment`; the app rejects a run whose manifest does not declare the mean-bias adjustment. Raw values and anomalies stay in the pipeline's diagnostics, which the app does not read. The adjustment removes mean bias only. Step 1 transforms apply to the adjusted monthly values, as they apply to observed monthly values.
- **H3 cell addresses as `int64` at resolution 6 (confirmed 2026-10-30).** H3 indices use 63 bits, so the values fit in a signed 64-bit integer. This matches the CMIP6 weather files; the ERA5-Land historical file stores the same values as `uint64`. The pipeline checks that every address is below 2^63 when it writes the forecast. `.harmonise_h3()` already accepts either type.
- **Data preparation starts with `t` (confirmed 2026-10-30).** The initial pipeline scope is monthly mean 2 m temperature, not a permanent limit on forecast variables. Minimum and maximum temperature (`tn`, `tx`) and rainfall (`r`) could be supported in future. `.STEP2_FORECAST_VARS` lists only `t` for now, so any model using another variable shows the current forecast as unavailable, including in the scaffold. Extend the available-variable list when retrieval, adjustment and validation for additional variables are ready. Rainfall also needs its own adjustment rule, including a near-zero-denominator policy.
- **Predictor-window rule (decided 2026-10-30).** A target month is allowed when every month its fitted predictors need is either an observed month up to the run's `observed_through` or a forecast month of the same run (lead 1 or later). A window is allowed when each of its target months is allowed. For an October 2026 initialization:
  - Default one-month lag (1-1): November to March are allowed, since each needs October to February, which are the initialization month or later forecast months. October is blocked, because it needs September, which is not observed.
  - "Same month" lag (0-0): October is allowed, since it needs only October, the initialization month. November to March are allowed.
  - One-to-three-month lag (1-3): January to March are allowed. November and December are blocked, since they need September.
  The rule is applied to the start choices and to multi-month windows, and it does not depend on which variable is selected.
- **Comparator and placement (decided 2026-11-02).** The forecast is not crossed with historical years. Each member gives one target-window aggregate (every household in each target month, weight `weight / L`). It is compared with a same-window reference: the same computation with observed weather for the same calendar months in each historical year. Historical (interview months) is not a valid comparator, because it mixes the seasonal cycle into the contrast. Results place each member in the reference distribution, for example "30% of members worse than the historical 1-in-10". There is no return period for the ensemble mean, and the member share is an indicator, not a probability. Seasonality: prefer calendar-month anomaly predictors with interview-month fixed effects. Keep each household's own `int_month` fixed effect; only the weather moves to the target month. Warn when the target months are rare in the training data. Details and the `int_month` bug: `roadmap/seasonal_forecast_review.md`, section 1.

## Open question: subseasonal forecasts

Offering a subseasonal product (ECMWF extended range, up to 46 days, issued twice weekly) for a one-month target fits the same flyout and the same downstream machinery. It is worth doing after the seasonal pipeline works, not in parallel.

For: it covers the next four to six weeks, where the seasonal monthly product is weakest; and the daily fields allow `tx35`, `tr`, `rx5day` and `r20`, which the monthly seasonal product cannot give, so fewer fitted models would be blocked.

Against: skill beyond about week two is low, so a one-month mean is a weak signal and the UI must say so. The data work is separate: different dataset, issue dates twice a week, reforecasts for calibration with fewer members and a different hindcast layout, and daily-to-monthly aggregation with partial-month handling.

If adopted, the UI change is small: a "Forecast type" toggle (Seasonal, Subseasonal) at the top of the flyout. Subseasonal fixes the window to one calendar month, the run select lists issue dates, and the strip shows only the month that fits inside the horizon. To keep that door open, the weather builder should key runs by product, run and member. Runs already carry `product` and `lead_unit` in `.step2_forecast_runs()`; the published catalogue must supply them.
