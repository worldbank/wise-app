# DuckDB 2.0 and Parquet v2 Investigation Plan

Date: 2026-10-01, updated 2026-10-22 with the first measured results (section 0). The implemented Step 2 serialization/progress work is summarized in [`optimization_tracking.md`](archive/optimization_tracking.md). Sections 1 to 3 are the original preview-era plan and are kept for the parts not yet measured. No production dependency, bundled extension or source-data file was changed; all measurements ran from a scratch copy of the repository with DuckDB 2.0.0 in an isolated library.

DuckDB engine 2.0 and Parquet v2 source encoding/layout are separate tracks. Neither is a prerequisite for Step 2 progress, preview or serialization. Neither authorizes production dependency changes or bulk source conversion.

## 0. Results, 2026-10-22

**Recommendation: DuckDB 2.0.0 is compatible but gives no measurable local speedup, so do not migrate for performance.** Migrate only if you want the 2.0 line for maintenance reasons, and then as a staged change (see the work list below). The first sequential comparison showed a 31 to 35 percent gain on the heavy workload; an interleaved A/B on identical local data (below) did not reproduce it, so that gain was machine drift between runs and is retracted. Parquet v2 and DuckDB native storage are dropped. The Databricks result is unreliable (other network use at the same time) and is not used for a decision.

Setup. Each engine ran in its own R process with its own library. The `duckdb == 1.5.6` pin in `DESCRIPTION` was relaxed in the scratch copy only, because `pkgload::load_all()` enforces it.

Parquet v2. On IRN historical weather (115 MB, written by DuckDB 1.5.0, Zstd, dictionary-encoded, 23 row groups) `PARQUET_VERSION V2` produces a byte-identical file, because DuckDB dictionary-encodes first and the values are quantized. With the dictionary disabled, v2 encodings (`BYTE_STREAM_SPLIT`, `DELTA_BINARY_PACKED`) give 179 MB against 168 MB for v1 and 115 MB with the dictionary, and scans were about 3x slower. Snappy was 183 MB. The source files are already well encoded; the Parquet v2 track is dropped for the weather data. Survey microdata and the large CMIP6 projection files were not tested. DuckDB native storage format 2 was not tested: the app reads external Parquet through views and has no persistent `.duckdb` files.

Open items and caveats:

- **Remote reads are untested.** The Databricks run was disturbed by other network use. If remote performance matters for the decision, repeat on a quiet network with more repetitions and check effective `httpfs` and async settings on 2.0 (`async_threads` defaulted to 32 and `read_ahead_depth` to -1 here).
- **Full-run fingerprints.** In the first full runs (`bfaslim`) the exact `result_fingerprint` and `prediction_fingerprint` hashes differed between engines, although separate prediction dumps were bit-identical. ## 1. DuckDB 2.0: Relevant, but Not a Blanket Speedup

The linked announcement is a **preview**. Its strongest applicable improvement is asynchronous Parquet I/O, particularly remote reads. It separates regular compute workers from I/O workers, overlaps range requests with decoding, and can help even with one regular query thread. Thus the current conservative `threads` policy is not sufficient by itself to bound the new engine's I/O concurrency.

Applicability to this app:

- **Remote weather/source reads:** highest-interest hypothesis. S3/GCS/Hugging Face/Databricks HTTP paths may benefit when request latency limits throughput. Verify the actual filesystem/extension path; do not assume identical Azure or custom HTTP behavior from an S3 benchmark.
- **Cold local scans:** possible smaller gain. Warm local cached scans may show little I/O benefit, and the previous BFA repetitions warmed filesystem/engine caches. A new connection does not clear OS caches or a mounted/cloud-synced file cache.
- **Weather joins/aggregates/pruning:** optimizer changes may help existing SQL, including improved `IN` pruning and aggregate pushdown. Inspect actual plans before attributing gains. Existing temporary materialization means later member scans are not repeated remote Parquet scans.
- **Recursive CTEs, Windows CLI materialization, VARIANT, triggers and Quack server mode:** not grounds for an expected Step 2 speedup. The advertised approximately 40x recursive-query gain is not an app benchmark; do not introduce a database server to pursue it.
- **DuckDB native storage v2:** a `.duckdb` database format, not Parquet v2. It does not automatically rewrite or improve existing external `.parquet` files. Persistent native files written by a new engine require an explicit rollback/readability policy.
- **R aggregation, prediction, forced GC, artifact RDS write/read and browser render:** not accelerated directly by a Parquet reader upgrade. Measure the affected share of end-to-end time, not just scan speed. DuckDB asynchronous I/O is also not Shiny async: a DBI call still blocks its calling R process until completion; retain mirai.

**Availability verified from r-universe metadata:** on 2026-10-01, the specifically named `duckdb.2.0.dev` package is `1.99.99.9000.1846`, R repository SHA `8a2d51e623a1d0f3c40cb0925156025af2d7ae4d`, vendoring engine commit `628d7c6db7c9dd373dc0c8ad6e355441611848ac`. macOS R 4.5.3 binaries are listed. The ordinary `duckdb` package on that repository is instead `1.5.6.9001`; merely adding r-universe to `install.packages("duckdb")` does not select the 2.0 preview. Locally, both `packageVersion("duckdb")` and `SELECT version()` report **1.5.5**; its settings table has no `async_threads` or `read_ahead_depth` entries.

The renamed preview flavor is not a drop-in namespace replacement for this app's `duckdb::` calls. For focused SQL probes, use its explicit namespace in a fresh isolated R process. For full app benchmarks, use an isolated pinned build exposed as `duckdb`, or a clearly documented investigation-only binding adapter with every namespaced call accounted for. Do not load multiple engine flavors into the same timing process or claim a CLI/Python scan proves R application compatibility. Keep existing installed libraries, production `DESCRIPTION`, extension directories and persistent database files untouched.

**Repository-specific compatibility gate:** Posit Connect installs bundled extension binaries through `R/fct_load_data.R:198-267`; the package currently ships `h3`, `httpfs` and `spatial`. Verify matching binaries for the pinned preview rather than reusing the current bundle. Azure additionally needs `azure`/`delta`, which are not in that bundle. The checked-in deployment manifest records 1.5.5, while `DESCRIPTION` does not constrain the DuckDB import version. Distinguish the actual deployed baseline from the guideline's preferred LTS baseline, and pin the accepted engine/extension set explicitly if an upgrade is eventually adopted.

**Benchmark design:**

1. Compare installed 1.5.5, the selected stable/LTS deployment baseline if different, and one pinned 2.0 preview. Record R package version, `SELECT version()`, engine/source SHA, platform, extensions and effective settings. Smoke-test DBI/dbplyr registration, SQL translation, H3 functions, httpfs/auth, Azure/delta where used, dates/timezones and connection cleanup first. Missing compatible extensions are a failed eligibility gate, not a reason to disable signature checks.
2. Use unchanged original files first. Run existing weather-only/Overview harnesses plus full Step 2 on BFA and IRN worst case. Preserve query text, projections, row ordering, caches, GC, memory and regular thread settings; report plan changes and exclusive scan/join/window/sort/fetch spans. Separate first connection/extension startup from steady-state runs.
3. Separate warm-local, documented cold-local and cold/warm target remote runs. Record bytes fetched, requests/retries and network throughput where available. Do not silently purge global OS caches or make billable remote transfers; use controlled environments and approved endpoints.
4. Inspect the preview's `duckdb_settings()` before tuning. The published I/O design describes default `async_threads` as four times system threads capped at 256, and `read_ahead_depth=-1` as memory-governed. Test a conservative I/O budget, record effective settings, and compare memory-governed read-ahead with a controlled alternative. `read_ahead_depth=0` disables look-ahead but is not proof the entire engine becomes synchronous; a positive depth is a job-count cap, not a byte cap, and the published design says it bypasses the queue memory budget.
5. Sample simultaneous tree RSS, allocator retention, spill bytes/disk space and I/O thread counts under several Connect processes plus Overview. DuckDB `memory_limit` is not a cap on total R/worker RSS. Prefetch may trade higher memory/CPU/network use for throughput; the vendor's concurrent benchmark explicitly shows that tradeoff.
6. Compare ordered weather frames and pipeline fields, join multiplicity/source IDs, missing/excluded/failed ledgers, all statistical outputs and Step 3/export behavior. Engine aggregation/optimizer changes can change floating-point reductions; classify differences explicitly rather than weakening exact BFA checks silently. Adoption requires stable deployable bindings/extensions and a rollback policy, not just faster local SQL.

Repository guidelines still prefer the stabilized LTS line for production and defer 2.0 adoption. This investigation adds a preview benchmark candidate, not an override of that policy.

## 2. Parquet v2: Test Encoding Separately from Layout

**Potentially useful, especially for remote weather data, but not established for these files yet.** Distinguish three separate concepts: DuckDB engine 2.0, DuckDB native storage format 2.0, and the Parquet writer's v2 encodings. Also distinguish a writer's format/encoding version from its `DATA_PAGE_V2` option: similarly named options in Arrow or other writers are not interchangeable promises of faster reads.

DuckDB's `COPY ... (FORMAT PARQUET, PARQUET_VERSION V2)` permits newer encodings including `DELTA_BINARY_PACKED`, `DELTA_LENGTH_BYTE_ARRAY` and `BYTE_STREAM_SPLIT`. These are lossless and already writable in DuckDB 1.2+, so **the installed 1.5.5 is sufficient to investigate them without a 2.0 upgrade**. Integer/date sequences and floating weather columns are plausible beneficiaries; dictionary encoding/compression may already handle repeated location/model identifiers well. Inspect actual encodings before assuming the inputs are v1 or poorly encoded.

The vendor's example reports approximately 30% smaller Snappy and 11% smaller Zstd files, but these are other datasets, not app estimates. Smaller files can reduce remote bytes; decoding CPU, row-group pruning and request overhead determine whether queries actually speed up. Encoding changes do not reduce full-year statistical requirements, R result matrices or final RDS/qs2 artifacts.

**Actual app read/write scope:** `load_data()` creates lazy `read_parquet()` views (`R/fct_load_data.R:381-398,684-712`); the loader has no writer-version switch that can change existing files. Historical weather projects H3/timestamp/selected variables and filters missing values/dates (`R/fct_get_weather.R:1135-1146`); H3 mappings and climate inputs have similarly narrowed projections (`1148-1171,1454-1458,1501-1524`). Country/survey/scenario filename selection is present, but the current code does not establish Hive partitioning or row-group layout. Remote raw weather slices are cached locally (`275-378`), while location-month materialization is reused (`380-465,1192-1269`). Cache writers use Zstd Parquet without explicit version options (`333-364,397-433`); batch result writers use Arrow defaults and are not the primary input-production pipeline. Benchmark upstream cold scans and local cache writes/hits separately, including the possibility that a source-encoding benefit disappears after the first cached read. The existing `dev/bench_w3_weather.R` cache-disabled local/optional Databricks setup is a useful starting point, not an existing encoding comparison.

**Proposed staged experiment:**

1. Inventory representative historical weather, climate and survey files with `parquet_file_metadata()`, `parquet_metadata()` and `parquet_schema()`: writer, physical/logical types, encodings, compression, compressed bytes by selected column, row-group count/size, key/date min-max overlap, nulls and Bloom availability. Record existing partition/file layout and current scan pruning; metadata itself may require remote requests.
2. Copy only approved representative data into a private temporary/benchmark directory; never rewrite production/source files. Hold row sequence, SQL types, row-group target, file count, compression codec and level fixed between v1/v2 variants. Include original files as the practical baseline. Verify physical metadata because rewriting an existing file can alter row-group boundaries even when the target count is fixed.
3. Compare v1/v2 under the current engine first, then cross the best candidates with the pinned preview. Start with a matched existing codec; compare Snappy versus Zstd low/default levels as a separate factor. Only after encoding effects are isolated, test a small row-group/clustering matrix. Do not combine sorting, repartitioning, codec and engine changes and credit the result solely to "v2".
4. Query the actual app projections and predicates, not only `COUNT(*)` (which may be answered from metadata). Include selected H3/weather-variable histories, climate reference and future-period selection, plus overview/survey scans. Measure physical bytes/requests, scan/decode/SQL/fetch time, end-to-end Step 2, first historical-ready time and isolated peak memory with cold/warm distinctions.
5. Preserve schemas, R attributes needed downstream, timestamps/timezones, 64-bit H3/IDs, NA/NaN/Inf and numerical values. For household survey rewrites, retain established source-row identity/order: sorting can change assigned `.svy_row_id` and residual/model behavior. For weather sorting/partition changes, preserve duplicates and explicitly restore canonical output order; never rely on physical file order.
6. Validate every real downstream reader/writer in the data-production chain (including deployed Spark/Databricks and Arrow/nanoparquet versions where used). Rewriting generic Parquet does not necessarily preserve pandas/Arrow key-value metadata. A Parquet header/version number alone does not prove all selected encodings or page types are supported. Never rewrite files inside a managed Delta table without its transaction/log tooling.
7. Adopt only if recurring read savings justify one-time rewrite/upload/storage costs and source/cache version changes. Keep prepared-weather cache identity synchronized with changed source generations. If source scan is a small fraction of warm BFA runtime, prefer proven artifact/GC/Results improvements instead.

Partition pruning, clustering on real filter keys, projection and sensible row-group sizes may matter more than the encoding version. They are hypotheses to evaluate from file metadata/query plans, not a recommendation for arbitrary H3-per-file partitioning or thousands of tiny files. Row groups must expose sufficient scan parallelism without excessive footer/request overhead; choose sizes from observed filtered rows/bytes and concurrency, not a universal value.
