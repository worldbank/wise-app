## Working rules

- One branch per batch off `dev` (`fix/rev-b1-deploy`, ...). Within a batch, one commit per finding ID, with the ID in the commit subject.
- A finding is `☑` only when (a) a regression test exists that fails before and passes after (or the item is config/docs and a reproducible command shows the fix), (b) the narrowest relevant `devtools::test(filter = ...)` passes, and (c) the Notes cell records the commit and what was verified.
- Numerical changes (CR-BUG-01/02, R2-BUG-01/02/03/06, R2-BUG-04) need a Decision log entry below with before/after BFA headline numbers, because outputs move.
- Performance changes follow `review/optimization_guidelines.md` §9 (equivalence gate, before/after timing and peak RSS on BFA and IRN). Timings in the report come from a 4-vCPU cloud container; re-measure locally and do not copy them.
- Run `devtools::document()`, `devtools::check()` and the full suite once per batch, with the tree quiescent. Regenerate `manifest.json` (`dev/00_make_manifest.R`) at the end of any batch that changes dependencies or `R/` files.
- Do not push or deploy from a batch without an explicit go-ahead.
- Benchmarks: use BFA 1x1 OLS (`WISEAPP_STEP2_WORKLOADS=one_ssp_one_period`, `WISEAPP_STEP2_MODELS=ols`) unless a larger payload is needed (user instruction 2026-10-07). The Step 3 harness (`dev/bench_step2.R` with `WISEAPP_STEP2_INCLUDE_STEP3=1 WISEAPP_STEP3_POLICIES=targeted_sp`) works on BFA; the `covariate` fixture needs an electricity column in the fitted model.

Batch order: B1 -> B2 -> B3 -> B4 are the report's "Now" list (§11 items 1-5). B5 is low-risk and can merge early. B6 follows the correctness batches so benchmarks are taken on correct numerics. B7-B9 are triage.

### WX-NEXT - further weather levers (closed 2026-10-08, no change kept)

Why each member frame has 310,500 rows: it is 596 locations x 270 months x 2 survey years, the historical weather window per location, not per household (7,128 households); the pipeline joins it back to households (`join_mutate`). The rows are needed. Light profile (`WISEAPP_WEATHER_PROFILE_LIGHT=1`, which skips the per-record serialisation and `ps`, so the wall time matches an unprofiled run: 39.2 s against 40.1 s) accounts for 87% of a BFA 2x2 run: consumer 16.1 s (pipelines 7.5 s, the rest harness wrapper plus `record_weather_support`), `future_collect` 7.6 s, `future_roll_compute` 4.8 s, `future_round_bin` 1.9 s, `future_rss_guard` 1.6 s (after the throttle), `roll_delta_lags` 1.0 s. A synthetic DuckDB test (596 locations x 270 months x 2 years x 16 members) showed the per-member time is mostly the string `ORDER BY` (0.074 s of 0.096 s; 0.002 s without it). Tried and rejected: (1) sort once when the period relation is materialised and filter per member without `ORDER BY`: 3.35 s against 3.23 s, no gain; (2) collect later members unsorted and fall back to the sorted query when their keys differ from the first member's: DuckDB does not return key order, so almost every member collected twice, 2x2 went 40.0 s to 43.1 s; (3) rewrite `.wx_round_weather_values()` without subsetting: identical output, 4 ms per member (0.25 s at 2x2), not kept. What is left is single-threaded DuckDB work (roll compute, collect), whose lever is the weather-threads decision (stay at 1 on Connect).
